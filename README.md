# AIGC生成数据看板

面向**贴吧 AIGC 内容增长**场景的运营数据看板。贴吧侧用 AIGC 能力针对用户在手百搜索的 Query 批量生成图文帖 / 视频帖，内容经「**评测 → 机审 → 人审 → 质量审核**」四道把关后分发到手百搜索结果页，用户在结果页点击并调起贴吧，从而推动贴吧用户增长。

看板把这条完整业务链路的每一环都做成了可观测、可下钻的视图，帮助增长产品经理完成「**监控生产 → 评估质量 → 发现异常 → 定位环节 → 采取行动**」。

> 看板里看到的所有内容，包括文本、Query、AIGC 评分、异常告警、案例说明，**全部为模拟数据**，由项目内脚本以固定随机种子生成，不含任何真实用户隐私信息，也不会调用真实大模型服务。

## 一、本地运行

纯前端项目，无后端、无数据库、无登录、无真实 AI API。

```bash
# 1. 确认环境：Node.js ≥ 18、Python 3 ≥ 3.9
node -v
python3 -V

# 2. 安装依赖
npm install

# 3. 启动开发服务器
npm run dev
# 浏览器打开 http://localhost:5173

# 其他命令
npm run build       # 类型检查 + 生产构建，产物在 dist/，base = '/'
npm run build:gh    # 同上，但 base 切到 /aigc_data_dashboard/（GitHub Pages 子路径用）
npm run preview     # 本地预览生产构建（http://localhost:4173）
npm run deploy:gh   # 一键构建并推送到 gh-pages 分支（详见第 9 节）
npm test            # 运行 67 项自动化测试（指标口径 + 异常规则）
npm run typecheck   # 仅类型检查
npm run gen:data    # 用固定种子重新生成 public/data/ 下的模拟数据
```

首次打开需加载约 **23 MB** 事件级模拟数据（本机实测 1–2 秒），期间有加载提示。建议在宽度 ≥ 1280 px 的电脑屏幕上浏览。

## 二、业务场景与目标用户

贴吧是手百搜索结果页上承接内容消费的主要载体之一。此前贴吧内容供给依赖用户自发生产，搜索结果页上常常「搜得到但没内容」。本项目引入 AIGC 批量生产能力，把内容供给从「等用户发帖」变成「按搜索需求主动生产」。

**完整业务链路**：

```
用户在手百搜索 Query → 贴吧 AIGC 生成图文帖 / 视频帖
  → AIGC 自动评测（6 维度打分 + 档位分流）+ 人工抽样复核
  → 机审（自动策略拦截）→ 人审（人工判罚）→ 质量审核（可读性 / 事实性）
  → 分发到手百搜索结果页 → 用户点击 → 调起贴吧 → 用户增长
```

| 环节 | 做什么 | 看板在哪一节观测 |
| --- | --- | --- |
| 用户搜索 | 用户发起搜索事件，写入 queryEvent | 筛选栏 / KPI「搜索用户规模」 |
| AIGC 生成 | 按 Query 生成图文 / 视频内容 | 三.3 内容供给 |
| AIGC 评测 | 自动评测模型 + 人工抽样复核 | 三.4 AIGC 内容评测（**占看板最大篇幅**） |
| 三层审核 | 机审 → 人审 → 质量审核 | 三.5 三层审核 |
| 分发与转化 | 搜索结果页曝光、点击、调起 | 三.6 分发与增长 |
| 异常监控 | R1~R6 6 条规则 | 三.8 异常监控 |

**目标用户**：贴吧增长产品经理。需要同时回答 5 个问题——**内容生产是否稳定、质量评估是否真实地识别劣化、审核是否卡住了供给、分发后有没有人点、点了能不能调起。**

## 三、这个看板解决什么问题

| 常见的运营盲区 | 看板的应对方式 |
| --- | --- |
| 只看到「内容量很多」，不知道搜到后被点了多少 | 把分发、曝光、点击、调起拆成独立环节，CTR 与调起成功率直接可算 |
| 把「内容没出来」笼统归为一类问题 | 拆分为**生成失败（技术链路）/ 评测不合格（质量链路）/ 审核拒绝（内容治理）/ 分类断供（供给结构）**，分母、归因、责任人都不同 |
| 三层审核看不出是哪一环出了问题 | 三层逐环展开通过率、拒绝原因、积压水位，并把各 Query 意图分类的人审拒绝偏离度单列 |
| 评测分数摆在那里，没和下游转化挂钩 | 「质量分 × 下游转化关联分析」一张表：按档位拆曝光 / 点击 / CTR / 调起，看质量分高是不是真的更容易被点 |
| 异常只在事后人工翻报表时才发现 | 6 条规则**实时计算**异常，每条带实际值 / 阈值 / 样本量、待验证假设与排查动作 |

## 四、核心功能

### 1. 全局筛选

日期范围（今日 / 近 7 天 / 近 30 天 / 自定义）+ 贴吧 + 内容类型（图文 / 视频）。切换后 KPI 卡、全部图表、漏斗、贴吧明细、异常列表同步重算；筛选栏底部实时显示「命中事件记录数」。

数据基准时间始终可见；超出数据范围或起止日期倒置时会给出明确提示，而不是静默出错。

### 2. 核心 KPI 概览（8 张卡片）

搜索用户规模 / AIGC 生成成功率 / 平均生成时长 / 三层审核通过率 / **AIGC 综合质量分** / 分发到手百 / 搜索结果 CTR / 调起贴吧成功率。

每张卡片除了数值，还给出**分子 / 分母**、与**上一等长可比周期**的对比，以及口径提示（例如生成中任务不计入成功率分母、待审内容不计入通过率分母、跨贴吧重复用户已去重）。

### 3. 内容供给（导航 1）

每日内容产出趋势、图文 vs 视频结构对比、生产漏斗（搜索 → 生成任务 → 成功内容 → 过审内容 → 分发）、各贴吧供给明细与可排序表格。

漏斗刻意做了**分层**：用户层统计「去重搜索人数」，内容层统计「内容条数」，两层不混算。

### 4. AIGC 内容评测（**导航 2 — 占看板最大篇幅**）

评测模型对每条产出内容在 **6 个质量维度**打 0~100 分并自动分档（优 ≥85 / 良 70~85 / 中 55~70 / 差 <55），人审按比例抽样复核，可计算人机一致率。**6 个子区块**如下：

1. **综合质量分与档位分布**：自绘 SVG 环图（优 / 良 / 中 / 差四档）+ 综合分 / 达标率（优+良占比）/ 不合格率（中+差占比）/ 评测覆盖率 / 人机分档一致率 / 最薄弱维度。
2. **质量趋势**：综合分与人机一致率按日并列折线，便于看「感官链路与判断标准是同步走还是背离走」。
3. **六维质量画像**：一表展示每维度的「权重 / 均分 / P10 / P90 / 不合格率 / 偏离六维均值 / 打分量 / 判读」，一眼看出短板在哪。
4. **图文 vs 视频 + 热力图**：左：图文 vs 视频两列均分与不合格率（声画一致性维度仅对视频帖有效）；右：5 类搜索意图 × 6 维度均分热力图，红→绿插值定位「哪个分类在哪个维度偏弱」。
5. **质量分 × 下游转化关联分析**：档位 / 内容数 / 占比 / 曝光 / 点击 / CTR / CTR 相对倍数 / 调起成功率，量化「分越高越容易被点吗」。
6. **低分归因 + 贴吧表现**：可按维度切换的低分原因分布（图视频 / 语义 / 文本三个分组下的具体问题标签）、低分内容 Top 10（点击行打开评测明细抽屉）、各贴吧 AIGC 质量表现表（点击触发全局贴吧筛选）。

**关键设计**：
- **不适用维度不预存布尔字段**：声画一致性仅视频帖打分；图文帖 `scores` 里没有 `av_sync` 键，由 `buildContentIndex()` 运行时判定。
- **加权归一**：综合分按适用维度的权重和归一，图文帖与视频帖可横向对比，不会因为视频帖少打一维就被抬高。
- **归属口径**：评测事件归因到「内容生成日」，与其他环节同口径。
- **评测来源口径**：自动评测全量打分，人工复核按 1/12 抽样；人机一致率按**分档**一致计算，不直接比绝对分数。
- **小样本二项噪声约束**：R6 三条子规则都放在「贴吧·区间」粒度（最小样本 200 条），避免贴吧·日只有 20~45 条时被噪声穿透。

### 5. 三层审核（导航 3）

机审 → 人审 → 质量审核的串行流水线，逐环展示通过量、通过率、待审积压水位；三环拒绝原因分布；以及**各 Query 意图分类的人审拒绝偏离度**——先扣除「当天整体审核变严」这类日级效应，再按样本量加权，因此长区间被平均后仍能看出拒绝是否集中在某类搜索意图上。

三层最终结论**不在内容上预存布尔字段**，由 `buildContentIndex()` 在运行时按 `contentId` 归拢 reviews 派生，保证结论与审核记录永远一致。

### 6. 分发与增长（导航 4）

分发量与曝光量趋势、搜索结果 CTR 趋势、**位次 CTR 衰减曲线**（第 1 位到第 20 位）、调起贴吧成功率与调起失败原因分布、各贴吧分发转化对比。

位次衰减是真实建模的：点击数由当日曝光量 × CTR 基线 × 位次系数派生，而非独立抽样，因此任意时间切片下的 CTR 都是稳定量。

### 7. 各贴吧一览与下钻

一张表并列六个贴吧的产出内容、三层通过率、AIGC 综合分、分发量、曝光量、CTR、调起成功率。点击「详情」打开抽屉，内含位次 CTR 曲线、内容类型拆解、调起失败原因、内容与审核状态原始样例、该吧命中的异常列表。

### 8. 异常监控与定位（导航 5）

| 规则 | 粒度 | 触发条件（演示阈值，可修改） |
| --- | --- | --- |
| R1 生成成功率 | 贴吧·日 | < 90% 且当日已完成生成尝试 ≥ 20 次；< 80% 升级为「严重」 |
| R2 平均生成时长 | 贴吧·日 | > 12s 且当日成功任务 ≥ 20 次；> 25s 升级为「严重」 |
| R3 三层审核异常 | 贴吧·日 | 任一环节拒绝率 > 40% 或待审积压 > 50 条，且该环节处理 ≥ 20 条；拒绝率 > 55% 或积压 > 200 条升级为「严重」 |
| R4 Query 分类断供 | 贴吧·区间 | 某 Query 意图分类从区间尾部往回连续 3 天日均供给 < 5 条，且区间 ≥ 7 天、该分类在本吧至少覆盖 3 个 Query；连续 ≥ 5 天升级为「严重」 |
| R5 分发转化下滑（扩展规则） | 贴吧·区间 | 搜索 CTR < 6% 或调起成功率 < 45%，且曝光 ≥ 500（CTR 口径）/ 点击 ≥ 50（调起口径） |
| **R6 AIGC 质量异常**（新增） | 贴吧·区间 | 任一评测维度不合格率 > 55% 且该维度打分 ≥ 200 条；或综合质量分 < 66 分；或人机分档一致率 < 72% 且人审样本 ≥ 40 条。R6 设计在区间粒度是为了避免小样本二项噪声穿透 |

R6 的「最小样本 200 条」是必要的防误报设计：贴吧·日每吧每天只有 20~45 条内容，噪声本身就能把不合格率打到 55% 附近。R6-1（单维度劣化）即使综合分仍为「良」，只要质量分加权后还有上升但人审抽样一致率下降，R6-3 就会独立告警，避免「综合分掩盖单维劣化」的盲区。

点击任意一条异常打开详情抽屉，可以看到：

1. **异常事实**：类型、严重度、粒度、日期、涉及贴吧、实际值 vs 阈值、样本量；
2. **对比证据**：同维度各贴吧的横向对比；
3. **分布证据**：生成失败原因、审核拒绝原因、耗时分桶、调起失败原因、低分原因分布或六维均分对比；
4. **原始样例**：直接取原始数据的具体记录，可逐条回溯；
5. **可能的原因**：全部明确标注为**待验证假设**，不把数据间接支持的判断写成已确认根因；
6. **运营建议与下一步排查方向**。

阈值集中定义在 `src/lib/config.ts`，页面底部同步展示当前生效的阈值。

### 9. 运营决策演示案例（导航 6，**已扩充至 6 个**）

内置端到端案例，每个都按「异常现象 → 数据证据（命中哪条规则）→ 可能原因（待验证假设）→ 运营动作」展开，并提供「一键复现筛选」按钮，可直接复现异常场景：

- **案例 1**：汽车吧生成失败率飙升 → 失败原因以「模型推理超时」为主 → 服务端容量排查
- **案例 2**：摄影吧视频帖变慢、图文帖不受影响 → 内容结构问题而非服务端问题
- **案例 3**：游戏吧人审拒绝率飙升、机审与质量审核正常 → 定位到人审环节内部
- **案例 4**：考研吧教育考试类 Query 断供 → 区分「真实供给缺口」与「被审核卡住的假断供」
- **案例 5**：健身吧 CTR 与调起成功率双降 → 增量流量以未装 App 的手百用户为主
- **案例 6（新增）**：汽车吧画面质量骤降 → **仅感官维度不合格率从基线 38% 升到 73%**，综合分仍 75.3 分不跌破阈值；语义类（事实性 / 内容-Query 符合度）维度不受影响 → 定位到画面生成模型而非通用 LLM，详情下钻到「AIGC 内容评测」看六维画像

## 六、模拟数据

### 来源

由项目内脚本 `scripts/generate_mock_data.py` 生成，**固定随机种子 `20261020`**，多次运行结果字节级完全一致，可复现。生成过程中人工注入了 6 类异常场景，因此在原始数据里都能找到对应证据。

### 结构

| 文件 | 内容 | 规模 |
| --- | --- | --- |
| `public/data/mock_bars.json` | 贴吧维度表 | 6 个贴吧 |
| `public/data/mock_queries.json` | 搜索 Query 维度表 | 80 个 Query，5 类搜索意图 |
| `public/data/mock_events.json` | 事件事实表 | 约 23 MB / 16.3 万条：搜索 6,504 · 生成任务 12,644 · 内容 12,839 · 三层审核 33,260 · AIGC 评测 13,773 · 分发 8,099 · 曝光记录 33,785（合计 27.3 万次逐次曝光）· 点击 22,746 · 调起 19,573 |
| `public/data/mock_meta.json` | 元信息 | 基准时间、种子、字典、6 个注入异常场景 |

数据关联链路（所有 ID 在原始数据中可逐条回溯）：

```
贴吧 barId → 搜索 Query queryId → 生成任务 taskId → 内容 contentId
  → AIGC 评测 eval（contentId 索引，区分 auto / human）
  → 三层审核 reviews（按 contentId + stage 区分）
  → 分发 distributeId
  → 曝光记录 impressionStat（按「内容 × 分发 × 日 × 位次」聚合）/ 点击 clickEvent / 调起 jumpBackEvent
```

曝光是量级最大的一环（27.3 万次），按「内容 × 分发 × 日 × 位次」聚合计数，不生成逐条曝光事件；点击与调起仍为逐条事件。这个取舍既让数据文件可控（约 23 MB），又保留了「同一内容」的可回溯关联链路。

### 复现

```bash
python3 scripts/generate_mock_data.py
```

### 注入的 6 类异常（均可在线验证）

| 场景 | 位置 | 时间窗 | 原始数据中的证据 |
| --- | --- | --- | --- |
| SCEN-01 生成失败率飙升 | 汽车吧 | 10-06 ~ 10-09 | 成功率从前一周 100.0% 掉到 81.1%，逐日最低 77.8%；失败原因中「模型推理超时」占 86% |
| SCEN-02 视频帖生成变慢 | 摄影吧 | 10-11 ~ 10-14 | 该吧平均耗时 13.5s~16.6s（阈值 12s）；拆开看视频帖 38.9s（前值 11.4s）、图文帖 4.3s（前值 4.2s）几乎未变 |
| SCEN-03 人审拒绝率飙升 | 游戏吧 | 10-12 ~ 10-17 | 人审通过率从前一周 83.9% 掉到 40.9%，逐日拒绝率 50.0%~72.7%；同期机审 10.8%、质量审核 7.3% 未变；拒绝原因中「品牌风险」占 78% |
| SCEN-04 Query 分类断供 | 考研吧 · 教育考试类 | 10-16 ~ 10-20 | 该分类日均产出从前一周 30.1 条掉到 0~2 条，其他分类供给正常 |
| SCEN-05 CTR 与调起双降 | 健身吧 | 10-09 ~ 10-19 | CTR 跌到 4.8%（阈值 6%），调起成功率从 68.0% 掉到 20.4%，「未安装贴吧 App」占失败原因 74%；分发量与曝光量均正常 |
| **SCEN-06 画面质量骤降** | 汽车吧 | 10-13 ~ 10-18 | 仅感官维度掉分：画面不合格率 84%（前值 38%）、综合分仍 75.3 分不跌破 66 分阈值；事实性 / 符合度等语义维度不受影响，定位到画面生成模型而非通用 LLM |

**统计截止时间**：模拟数据基准时间为 `2026-10-20 23:59:00`（Asia/Shanghai），覆盖 60 天业务数据（2026-08-22 ~ 10-20）。它不是真实当前时间。

## 十、注意事项与已知限制

1. **全部为模拟数据**，不代表任何真实业务的经营情况，也不含真实用户隐私信息。
2. 模拟数据基准时间固定为 `2026-10-20 23:59:00`（Asia/Shanghai），不是真实当前时间。
3. 默认「近 30 天 + 全部贴吧」会显示约 **16 条异常，全部可追溯到 6 个注入场景**（R1×4 / R2×3 / R3×6 / R4×1 / R5×1 / R6×1），没有一条是日常波动误报。这一点是靠刻意标定的：各规则的告警阈值都留足了 3σ 以上余量，避免常态水位被误判。
4. 事件文件约 23 MB、纯前端聚合，加载与筛选在本机范围内够用；真实生产环境应改为服务端预聚合接口。
5. 数据量再大一个量级时，前端全量聚合会有明显压力，届时需要把 `selectData` / `aggregate` 下沉到服务端。
6. 仅在 Google Chrome 上做过完整验证，未覆盖 Safari / Firefox，也未做移动端适配（布局最小适配到 900px 宽度）。
7. 「调起贴吧」的真实承接链路（唤端成功率、落地页加载）没有数据支撑，案例 5 的相关判断已标注为待验证。

## 附录 B：部署到 GitHub Pages

项目已配好一键部署脚本（`scripts/deploy_gh_pages.sh`），推到 `gh-pages` 分支即可。

```bash
# 1. 把项目推到 GitHub（替换为你自己的仓库地址）
git remote add origin https://github.com/<your-user>/aigc_data_dashboard.git
git push -u origin main

# 2. 第一次：在 GitHub 网页上把 Pages Source 改为 gh-pages / (root)
#    https://github.com/<your-user>/aigc_data_dashboard/settings/pages
#    Source = "Deploy from a branch" → Branch: gh-pages → Folder: / (root) → Save

# 3. 之后每次发布：
npm run deploy:gh
```

页面生效后访问 `https://<your-user>.github.io/aigc_data_dashboard/` 即可。本地开发不受影响（`npm run dev` 仍以 `/` 为 base）。
